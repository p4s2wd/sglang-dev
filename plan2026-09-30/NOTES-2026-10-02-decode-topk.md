# 2026-10-02 decode 变慢:元凶定位与并行化原型

接 `NOTES-2026-10-02-longctx.md` §二。本文是那一条线的续:找到了增长项,
量化了并行化的收益,并把一个不平凡的**正确性前提**测了出来。

## 一、元凶:`_topk_transform_paged_triton_kernel` 只用 1 个 block

四个 PP stage 的 grid 完全一致(取自 torch profiler trace 的 `args.grid`):

| kernel | 短(440 tok)grid | 长(150K)grid | 短合计 us | 长合计 us | 增长 |
|---|---|---|---|---|---|
| **topk_transform_paged** | **[1,1,1]** | **[1,1,1]** | ~1,500 | **46,807–58,013** | **32–39×** |
| mqa_paged_smallq | [32,1,1] | **[2050,1,1]** | ~3,000 | 28,400–35,130 | ~10× |
| headshared_sparse (MLA) | [1,4,8] | [1,4,8] | ~10,000 | 16,309–23,153 | 1.7× |

单次 launch:25.06 us(440 tok)→ **911.9 us**(150K tok)。
反解固定开销 ~22 us、每轮 ~3.04 us,150K 上下文即 293 轮。

**`grid = (scores.shape[0],)` = 只按行并行。decode 时 bs=1 → 1 行 → 1 个 128 线程 block
跑在 68 个 SM 上 = 1.5% 占用率**,而它扛的是 O(上下文) 的串行归约。

对照:索引器 `mqa_paged_smallq` 的 grid 随上下文从 32 涨到 2050,**并行度与工作量同步**
——它的 10 倍增长只是"活变多了",不是效率问题。**只有 topk 是并行度与工作量脱钩。**

量级:topk 四 stage 合计 209,402 us / 24 token = **8.7 ms/token**,约占长上下文 decode 的 16%。

## 二、基线(当前上线配置,池 267,776)

`dec_ctx_probe.py`,115,092 token → **52.16 ms/token(19.17 tok/s)**,spread 0.4%。

⚠ 156,429 token 那档测出 218 tok/s 的**物理不可能值**:池满时第二次调用触发驱逐+重算,
把"两次缓存命中相减"的方法算崩了。**这个假象本身就是池装不下的信号,不是噪声。**

## 三、并行化原型:收益真实,但有一个正确性前提

top-k 对划分满足结合律,所以"每分片取 top-K,再取并集的 top-K"是**精确**的,不是近似。
原型(`mqa_topk_split_bench.py`):kernel A 按 slab 并行求 top-K 写 partials,kernel B 归并。

| seq_len | 基线 us | split32 | split64 | split128 | 最佳加速 |
|---|---|---|---|---|---|
| 4,096 | 109.4 | 125.6 | 109.2 | 125.0 | 1.0×(无收益) |
| 37,500 | 906.6 | 227.7 | 296.5 | 526.6 | **4.0×** |
| 150,000 | 3,636.1 | 330.1 | 470.2 | 705.5 | **11.0×** |

**收益是真的:长上下文下 4–11 倍。** 短上下文无收益,所以需要按 seq_len 分派。

## 四、★ 关键发现:那个 merge 方式**不是**幂等的

生产 kernel 的归并写法是

```python
acc = tl.bitonic_merge(acc)
acc = tl.maximum(acc, tl.topk(candidate, K_POW2, dim=0))
```

而 `candidate` 本身就是 `tl.topk(packed, K_POW2)` —— **同一个值上调用了两次 `tl.topk`**。

把已排序的分片喂进去(而非原始 score 块)时,它**不再正确**:

| cap | npart | production shape | sort acc first | sort both, no bitonic_merge | sort + sort(max) |
|---|---|---|---|---|---|
| 4,096 | 8 | **246 wrong** | 248 | 184 | 184 |
| 37,500 | 8 | OK | OK | 431 | 431 |
| 37,500 | 25 | **11 wrong** | 11 | 471 | 471 |
| 150,000 | 8 | OK | OK | 436 | 436 |
| 150,000 | 30 | OK | OK | 436 | 486 |

(`topk_merge_variants.py`,分片由 torch.topk 生成,所以错的只有 merge 本身)

**"sort both" 那两列错得更多,说明它们连生产的语义都不是。** 而"production shape"在
npart=8/30 对、npart=25 错 —— 也就是说**这个写法只是近似正确,靠迭代次数多才收敛到精确**。
生产 kernel 之所以精确,是因为它迭代 74/293 次(每次 512 个**原始 score**);
而合并 25/30 个分片时精度就塌了。

## 五、一个重要的反向验证:**生产 kernel 是正确的**

担心 `tl.maximum` 对两个降序数组取逐元素最大会丢元素(例:A=[9,8,7], B=[10,1,2] → [10,8,7],
正确答案 [10,9,8],**丢了 9**)。实测:

```
seq_len=2048   逐位相同=True  集合相同=True  交集=512/512
seq_len=37500  逐位相同=True  集合相同=True  交集=512/512
```

**与 `torch.topk` 逐位一致,没有既有缺陷。** 我先前的分析错了:`tl.bitonic_merge` 会破坏
降序序,所以那不是"逐元素最大",而是在构造一个 bitonic 排序结构。

**所以 kernel 本身没有 bug —— 卡住的是"如何把它的归并步骤复用到已排序的分片上"。**

## 六、结论与下一步

**没有上线任何东西。** 收益已量化(4–11×,占长上下文 decode 约 16%),
但 merge 的精确性前提没搞清楚之前不动生产代码 —— 一个"快 11 倍但选错 11 个 KV 页"的
top-k 会改变模型输出,比慢 16% 糟糕得多。

# 七、结案(12:00–15:10)

上面第六节的两个结论**都是错的**,而且是同一个错误。先说错在哪,因为这才是本次真正
值得记下来的东西。

## 七.1 符号性:packed key 是负 int64

`packed = (key << 32) | col`,其中 `key = float_bits ^ 0x80000000`(**正**浮点)。
`float_bits ^ 0x80000000` 最大到 `0xFFFFFFFF` —— **超过 `0x7FFFFFFF`** ——
所以左移 32 位后 bit63 置位,**packed 作为 int64 是负的**。实测约一半真实分数如此:

| cap | 负值占比 | 最小 packed | int64 有符号排序 | uint64 无符号排序 |
|---|---|---|---|---|
16,384 | 49.8% | −5.08e18 | **wrong 512/512** | **exact** |
150,000 | 50.1% | −5.15e18 | **wrong 512/512** | **exact** |

有符号降序排序会把**最大的分数排到最后**,取出来的是最小的 512 个;而零填充
(比任何负数都大)会占满输出槽位。

生产 kernel 一直是对的,因为它的 `acc` 是 `tl.uint64`,比较走无符号。
**是我的原型把它存进 int64 了。**

**连带后果**:第六节「生产 merge 对已排序分片不精确(错 5–251 个)」**整条结论作废** ——
那个现象同样是符号性造成的。改成 uint64 后,**16 组形状 × 4 种组合 = 64/64 全 exact**,
生产递推本来就是精确的。

最阴险的一点:**参考系也被同一个 bug 污染了**。`torch.sort` 对 int64 也是有符号排序,
所以拿它当"真值"时,错误答案和错误实现给出了相同的顺序:

```
无符号 key 排序 == torch.topk indices        → True
torch.sort(packed int64) == torch.topk indices → False
```

## 七.2 精确 merge:改用全排序,而不是递推

不依赖递推的近似性,merge 定义成**对拼接后的分片做一次完整 `tl.sort`** 取前 K_POW2。
这是定义上精确的。代价有两个,都是硬约束:

- **shared memory**:`tl.sort` 开销随排序宽度增长,SM75 只有 64 KB。
  `FANIN=16`(8192 int64)要 256 KB,**launch 直接失败**。所以 `FANIN=2`。
- **多级要有 padding**:早期版本每级都用固定 `FANIN`,某级分片数不足时会**越界读**;
  它看起来正常只是因为越界读到零填充,而零排到最后动不了赢家 —— 有一部分"精确"是运气。

我自己的 harness 也犯了同一个错:`cur.reshape(-1)[:KP]` 在 `rows>1` 时让**每一行都拿到
第 0 行的答案**,rows=1 时完全看不出来。

## 七.3 生产集成

三个 kernel:分片 → 中间级排序 → **末级融合 page-table 变换**(不融合要多付约 6 个
torch op/token,对一个 130 us 的 kernel 不便宜)。保留 IMA 的 `page_table_width` 界。

两条硬约束决定实现形态:

- **分派依据必须是 host 侧量**。`seq_lens` 在 graph 内是 device buffer,每步变,
  **不能用来选 launch**;`scores.shape[1]` 和 rows 对 graph bucket 是固定的。
- **缓冲必须缓存且永不释放**。graph 把指针烤进去了,释放后换个地址重分配 = 重放时
  读别人的内存。另加总预算,超了退回单程序 kernel,而不是不安全地分配。

阈值全部实测,不猜:

| | 1 row | 8 | 16 | 32 | 128 |
|---|---|---|---|---|---|
|width 37,500 | 5.9× | 3.6× | 1.7× | **0.93×** | 0.41× |
|width 262,144 | 25.8× | 6.8× | 3.4× | 1.6× | **0.80×** |

rows 多时原 kernel 本来就有并行度(它就是 `rows` 个 program),所以只对小 rows 有意义。
**下限 8192**(6144 时 0.84×、8192 时 1.66×)。

## 八.1 崩了

17:07 PP0 崩在一个 257K prefill 的中途:

```
torch.OutOfMemoryError: Tried to allocate 44.00 MiB.
GPU 0 has a total capacity of 21.49 GiB of which 35.25 MiB is free.

If reserved but unallocated memory is large try setting

```

**35 MiB 空闲 + 120 MiB 被缓存但碎成小块,凑不出连续的 44 MiB。**
日志归档 `res/crash_257k_prefill.log`。

## 八.2 那 44 MiB 是什么

栈是 `_execute_extend` → MoE fp8 路径 → `fp8.py:3271`:

```python
down_slots = torch.empty((num_slots, hidden), dtype=torch.float16, ...)
```

而 `num_slots` 是 align 缓冲的**容量**:

```
num_slots = num_tokens * topk + (E+1) * (block_m - 1)
          = num_tokens * 6   + 257 * 15
```

chunk=256 时 = 1,536 + 3,855 = 5,391 行 × 4096 × 2 B = **44.2 MB**,与报错完全吻合。

**关键在那 3,855 行:它是纯 padding,和 token 数无关。** 所以调小 chunk 几乎没用:

| chunk | num_slots | inter_slots |
|---|---|---|
256 | 5,391 | 44.2 MB |
128 | 4,623 | 37.9 MB |
16 | 3,951 | 32.4 MB |

每层地板约 **63 MB**(inter_slots + down_slots 两个缓冲),**无论 chunk 多小都下不去**。
作者自己的注释也承认:"at decode is 3861 rows against 6 live ones"。

## 八.3 修法:先治碎片,没动 block_m

`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`(launcher 里可覆盖)。
理由:报错明说碎片,而 `num_slots` 那个 padding 项要靠改 `block_m`(16→8 能省约 34 MB/层),
但那会动 GEMM 的 tiling,是另一件事、另一份风险。**先做便宜的、能被验证的那一半。**

结果(冷 prefill,prompt 里每 20 词插随机 nonce 破坏 radix 前缀,否则第二次会被缓存吃掉——我第一次
就是这么骗自己的:三次都报 4300–5100 tok/s,那是缓存命中):

|---|---|---|
256,933 | 482.2 s | 532.8 |

## 八.5 代价:池变小,parity 不再逐字节一致

- **池 267,776 → 264,192**(expandable_segments 预留更大的虚拟段)。仍 > 262,144,
  但余量从 5,632 缩到 2,048 token。
- **parity 从 6/6 变成 5/6**:prompt[2] 在第 129 字符分叉,两个版本都通顺、答的是同一问题,
  只是措辞不同。**同配置两次抓取逐字节一致**,说明确定性没坏;变的是分配器给的地址 →
  kernel 选路不同 → logit 微小差异 → greedy 换一个词。GSM8K 严格口径反而从 0.890 升到
  **0.910**(宽松 0.980),闸门通过。

**所以这是良性的数值噪声,但它确实改变了可观测行为,不能说"和之前一模一样"。**

## 八.6 还没解决的

`num_slots` 的 padding 项(每层 63 MB 地板)是结构性的。要动就得改 `block_m`(16→8,
padding 从 3,855 行降到 1,799 行,每层省约 34 MB),那会改 GEMM tiling,必须单独验证。
**没有做。**

可靠性样本只有 3 次冷 prefill,而崩溃只发生过 1 次 —— **3 过 1 崩不足以称为"可靠"**,
只能说"不再立刻崩"。

## 八.7 补测:碎片之后再压 256K(19:00–19:45)

第八节那 3 次冷 prefill 都在服务器生命的**早期**,而原始崩溃发生在服务过 GSM8K 和
batch 扫描**之后**。碎片随进程寿命累积,所以那 3 次不构成复现。补一轮正确设计的:

`pf256k_stress.py` —— 每轮先跑 6 分钟混合负载(长度 200/900/4K/16K/40K 随机、
bs 1–8 随机、newtok 1–400 随机,故意让分配器保留各种尺寸的块),再发一个冷 256K prompt。

| 轮次 | prompt | +补全 | 总计 | 墙钟 | prefill tok/s |
|---|---|---|---|---|---|
0 | 257,896 | 800 | 258,696 | 442 s | 584 |
1 | 258,957 | 800 | 259,757 | 438 s | 591 |
2 | 259,908 | 800 | 260,708 | 461 s | 564 |

**3/3 通过,崩溃计数 0。** 加上第八节的 3 次,**6/6 冷 prefill 通过(256,933–259,908)**,
而改之前同类请求崩过 1 次。

**prefill 吞吐没有代价**:564–591 vs 早前的 532–574,区间重叠。担心的那 9% 不存在 ——
那是不同 prompt 内容导致 MoE 路由不同,不是分配器的锅。

## 八.8 更正:`block_m` 不该动(读代码后)

第八节说"每层 63 MB 地板,`block_m` 16→8 能省约 34 MB,值得单独验证"。读完
`moe_align_block_size` 后这个说法要收回一半:

```python
max_num_tokens_padded = topk_ids.numel() + (num_experts + 1) * (block_size - 1)
```

padding 项确实是常数(chunk 降不下来,这部分成立)。**但"纯浪费"不成立:**

| | 容量 | 实际需要 | 浪费 |
|---|---|---|---|
prefill chunk 256 | 5,391 行 | ~4,096 行 | **仅 24%** |
decode(1 token) | 3,861 行 | ~96 行 | 96% |

prefill 时 1,536 个 token-expert 对摊到 256 个专家、每专家约 6 个,向上取整到 16 的倍数
≈ 4,096 行 —— **缓冲在 prefill 阶段基本用满,可省的不到 24%,还要拿 GEMM tiling 去换。**

浪费大的地方是 decode(96%),而 decode 的缓冲被 CUDA graph 缓存复用、只驻留一份,
不是峰值问题。

**结论从"还没做"改成"不该做"。** 真正的病根是碎片,已经治了。

## 八.9 这个测试自己踩的坑(记录下来)

1. **固定 prompt → radix 缓存吃掉 prefill。** 三次都报 4300–5100 tok/s,那是缓存命中。
   解法:每 20 词插一个随机 nonce 破坏前缀。
2. **`random.Random(target*7919+newtok)` 种子只依赖 target**,两次"不同"轮次生成了
   完全相同的 prompt,又一次变成缓存命中。种子必须每轮不同。
3. **nonce 宽度不定 → token 数不定。** `randrange(10**12)` 的 token 数在 104.99–106.00
   之间跳,我按 104.99 反算词数,连续三次撞 400。
   **不该预测 token 数。** 改成撞 400 就自动缩 3% 重试,直接用服务器返回的实际值。

# 十一、B 阶段:decode 到底被什么绑住(21:00–23:30)

目标:decode 27 tok/s,内存地板约 370,差 14 倍。找那 14 倍在哪。

**这一节有我今天最大的一次自我纠正。**

## 十一.1 我之前算错了「GPU 忙 4.8%」

之前的结论是「GPU 只忙 4.8%,93% 的时间在等主机」,依据是 trace 里
`kernel 总时长 / trace 跨度`。

**分母错了。** torch profiler 把 span 撑长了(kernel 时长本身由 CUPTI 实测,是准的,
但 span 被 profiler 开销放大了)。正确算法是拿 kernel 总时长除以**真实 step 时间**:

- 4 级 kernel 总时长 = **623.1 ms**,覆盖一次 24 token 生成
- 同样 24 个 token 未抓 profile 时要 24 / 26.86 = **894 ms**
- → **GPU 忙 623 / 894 = 70%**

**所以不是「93% 在等主机」,而是 GPU 有 26.0 ms/token 的活要干,step 只有 37.3 ms。**

连带作废:基于该结论推出的「decode 是主机侧问题」整套叙事,以及「PP 主机端开销是
大头」这个方向。

## 十一.2 每 token 的 GPU 工作量(4 级合计)

| 家族 | ms/token | 占比 | 次数/token |
|---|---|---|---|
**nccl** | **10.22** | **39.4%** | 52 |
other | 8.03 | 30.9% | 448 |
gemm | 5.30 | 20.4% | 268 |
elementwise | 0.96 | 3.7% | 328 |
topk | 0.66 | 2.5% | 12 |
attn | 0.43 | 1.7% | 146 |
moe | 0.34 | 1.3% | 64 |
memcpy | 0.03 | 0.1% | 16 |
**合计** | **25.96** | | |

**NCCL 是单项最大:10.22 ms/token、52 次集合通信、平均每次 197 us。**

**但这不是带宽问题,是延迟问题** —— kernel 时长中位数 4 us,2080 Ti 上一堆微秒级
kernel 串不起来。CUDA graph 里 NCCL 是图上的节点,与其他 kernel 串行执行,
**没有 comm/compute 重叠**。

## 十一.3 拓扑是被算术锁死的

我实测的字节数:专家 157.44 GB、注意力 5.99 GB、共享专家 1.16 GB,共 43 层。

| 方案 | 每层每卡 | 装得下? |
|---|---|---|
**TP2(现状)** | (3.662+0.139+0.027)/2 = **1.914 GB** × 11 层 = **21.05 GB** | 勉强(= 卡 21.49 GB) |
TP1 | 3.828 GB × 6 层 = 22.9 GB | **实测 OOM 崩服** |
TP1+EP2 | 3.662/2 + 0.139 + 0.027 = **1.997 GB** × 11 = 21.97 GB | **比 TP2 还多** |

**关键:整台机器 98% 的显存被权重占满**(167.81 GB 权重 / 8 × 20.6 GB 容量
= 164.8 GB)。任何不完美均分权重的拓扑都会 OOM。

已实测排除的四种:

- **TP1×PP8** —— 启动即 PP0 OOM(`Tried to allocate 1024 MiB, 255 MiB free`)。
  原因:TP 不切时每卡扛**整层**,43 层分 8 卡至少 6 层/卡 = 22.9 GB。归档
  `res/crash_tp1pp8_oom.log`。
- **PP2×TP4** —— 每级 21–22 层 = 40+ GB,装不下。而且方向本来就错:TP 变宽会让
  all-reduce 更贵,不是更便宜。
- **EP** —— 只对专家生效不对注意力生效,每卡显存**比 TP2 还高**;且 PP4 时每级正好
  2 卡,已被 TP2 用满,**没有独立的 EP 轴**。
- **PP pickle 路径** —— 见 十一.4,稳态只占 0.1%。

## 十一.4 PP 握手:稳态 0.015 ms,不是瓶颈

加了门控诊断(`SGLANG_OPT_PP_HANDOFF_DIAG`,commit `e8e7421c4f`)在生产路径上分解:

| | 耗时 |
|---|---|
SEND metadata | 0.001 ms |
SEND tensors(异步 isend) | 0.117–0.148 ms |
**RECV metadata(`recv_object`)** | **0.014 ms** |
RECV irecv / allgather | 0.000 ms |
**RECV 合计** | **0.015 ms** |

载荷:一个 `(6, 16384)` fp16 张量(192 KB)+ 177 字节 pickle。

**3 跳合计 0.045 ms,占 37.3 ms 步的 0.1%。不值得改。**

**第一次测出 0.35–1.07 ms 是启动期的假象**,因为诊断只在每个 rank 第一次 handoff
触发。改成周期采样(每 N 次)后拿到稳态值。

那 profile 里 25% 的时间在哪?在 **`_pp_commit_comm_work`(self 19.7%)** —— 等之前
发出的异步发送真正在 GPU 上完成。**发送本身是微秒级,完成是毫秒级**,因为 bs=1 时
对端还在算上一个 token。**这个 wait 吸收的是流水线停顿本身,不是它自己的开销。**

## 十一.5 主机侧到底用了多少 CPU(不用 profiler 的测法)

`dec_cpu_time.py`:读 `/proc/<pid>/stat` 的 utime+stime,和墙钟比。**不需要把时间
归因到任何 Python 帧,所以不会被「采样落在哪里」骗到。**

3000 token @ 8K bs=1,墙钟 37.3 ms/token:

| 级 | CPU ms/token | 占墙钟 |
|---|---|---|
PP0_TP0(最忙) | **20.5** | 55% |
PP2_TP0 | 20.0 | 54% |
PP1_TP0 | 18.5 | 50% |
… | 15.5–18.3 | 42–49% |

**每一级每 token 烧 15–20.5 ms CPU。** 8 级合计 142 ms/token,分摊在 8 个进程。

## 十一.6 B 阶段的结论

bs=1 的 decode 由三件事共同绑定,**都不是可以靠调参解决的**:

1. **GPU 26.0 ms/token**,但 kernel 时长中位数 4 us —— **延迟受限,不是带宽受限**
2. **每级 15–20.5 ms CPU**,其中约一半的 self time 在 PP 通信机制上,而那主要是在
   **等对端**(bs=1 下流水线必然串行:token n+1 要等 n 走完 4 级)
3. **拓扑被显存算术锁死**,换不了

**所以 60–100 tok/s 这个目标,在 bs=1 上需要动拓扑;而动拓扑需要动显存 —— 这两件事
在这台机器上互斥。**

剩下还能做的,是个位数百分比量级:
- 融合 all-reduce 开关(`enable_fused_moe_sum_all_reduce`、
  `enable_flashinfer_allreduce_fusion`,现在都是 False)。每层省 1 次通信,
  44 → 33 次,乐观估计省 2 ms(**+6%**)。
- 每级那 ~10 ms 非通信 Python。

## 十一.7 还没查的一段(留给下次)

**8K → 131K 掉 20%**(26.9 → 21.4),这段**不是 top-K**(top-K 在 8K 以上才启用,
而它的效果是让曲线在 131K 之后变平)。这段约 5 ms/token 的来源没查。

**顺带:我在这一节犯的错,和之前几次是同一类** —— 拿一个测不准的仪器
(torch profiler / 一次性采样 / 别人的参考系)得出过于肯定的结论。
**今天的教训是:先问「这个测量在什么条件下可信」,再读数。**
